# 设计文档：为什么这么做

这份文档不讲"代码在做什么"（读代码就知道），只讲**为什么这么选、替代方案是什么、代价在哪**。
面试时会被追问的，是这一层。

---

## 0. 这个项目要回答的问题

> 面向中文财会准则与会计制度，把检索从"能跑"做到"**说得清好在哪、差在哪**"。

大多数 RAG 项目停在"能跑"：接个向量库，调个 embedding，拼个 prompt，看起来能用。
但"能用"是不可验证的——换个切分方式会不会更好？加个重排值不值那点延迟？答错了是检索的锅还是生成的锅？

本项目把这些问题变成**可测量的数字**。

---

## 1. 语料层：为什么清洗是第一步

**原始语料什么样**：549 篇财会准则与会计制度原文，从财政部会计司网站抓下来的（政策发布 338 / 政策解读 211）。每篇前面有十几行网页导航（"财政部微信""官方抖音号""移动客户端下载"），后面挂着附件下载链接和 JavaScript 片段（`var handel=document.getElementById(...)`）。

**不清洗会怎样**：这些噪音会被切进片段、算进向量、参与检索。
最坏的情况是——用户问"金融资产公允价值怎么披露"，检索命中的片段里有一半是 `getElementById`。

**做法**：定位 `当前位置` 标记，之后才是正文；遇到"相关文章""附件下载"或 JS 特征即截断。
实测平均正文 3,571 字，**平均去掉 84.3% 的字符**，全是噪音。

**顺带抽出的元数据**：

| 字段 | 为什么重要 | 本语料覆盖 |
|---|---|---|
| `doc_no`（文号） | 让每条结论可溯源到具体文件，不是"某准则说" | 404/549 |
| `issued`（发布日期） | 支持"按时间过滤"——问 2026 年的问题不该召回 2016 年的旧规 | 549/549 |
| `effective_from`（施行日期） | 准则常有过渡期，这是判断"现在适不适用"的依据 | 140/549 |
| `valid_to`（执行截止日） | 税务语料的时效判断基础；本语料用的是「自…起施行」措辞，抽取结果为空 | 0/549 |

**关于 `valid_to` 为空**：这不是 bug。会计准则写「本准则自 2027 年 1 月 1 日起施行」，
而不是「执行至 2027 年 12 月 31 日」——后者是税收优惠文书的写法。
链路保留该字段是为了换语料时能用，本语料的时效过滤实际由 `issued` 承担。

**取舍**：清洗规则是**基于模板的确定性规则**，不是用 LLM 清洗。原因：549 篇来自同一套模板，规则足以覆盖；用 LLM 清洗会引入不确定性，且每次重跑结果可能不同——评测需要可复现。

## 2. 切分层：领域感知 vs 通用做法

**三种策略，对应三种思路**：

| 策略 | 做法 | 代表什么 |
|---|---|---|
| `fixed` | 每 300 字一刀，重叠 50 字 | 最朴素的基线 |
| `recursive` | 按段落→句号→逗号逐级断（LangChain 默认思路） | 通用工程的常见选择 |
| `article` | 按「一、」「二、」「第X条」条款边界切 | **领域感知**：政策文本天然有条款结构 |

**为什么怀疑通用切分**：准则的一条就是一个语义单元。"（一）采用估值技术确定公允价值的……"被从中间切断，模型看到半条，自然答不准。

**但必须诚实的地方**：已有研究（arXiv 2410.13070《Is Semantic Chunking Worth the Computational Cost?》）实测**复杂切分在真实文档上常打不过简单切分**，embedding 质量的影响远大于切分策略。

所以这个项目的立场是：**不预设结论，跑数据说话**。`article` 到底比 `fixed` 好多少（或者是否真的更好），看消融结果。这也是本项目相比"我用了很牛的切分"更可信的地方。

**消融跑完的结果是——三种切分都没跑赢基线**：条款切分 Recall@3 比固定切分低 1.5pp，
递归切分基本持平。这和上面的怀疑方向一致，但比预期更彻底：连"领域感知切分"也没有带来增益。

原因大致能对上：**金标是文件级的**，一份准则被切成几十个片段后，
模型排名靠前的往往还是同一份文件的多个片段——切得更细并没有改善"该文件进没进 top-3"，
反而因为片段更碎、单片段信息量下降，把 Recall@1 拖低了。

**这条结论要说清楚适用边界**：它是「这份语料 + doc 级金标」下的结论。
若下游直接读 top-1 片段，切分粒度的重要性会明显上升，不能直接外推。
把边界写出来，比给一个漂亮但不可迁移的结论更有用。

## 3. 检索层：为什么是召回 + 重排两段式

**两种检索范式，各自的长短**：

| | 原理 | 强项 | 弱项 |
|---|---|---|---|
| 向量检索 | 查询和文档各算一个向量，比距离（双塔） | 语义相近能召回（"估值技术确定公允价值"↔"公允价值怎么算出来的"） | 文号、数字、专有名词会被"糊"掉 |
| BM25 | 字面词频统计（Okapi 公式） | 精确匹配强 | 换个说法就召不回 |

**所以两者都要**，用 **RRF（Reciprocal Rank Fusion）** 融合：

```
score(d) = Σ_r  1 / (k + rank_r(d))     k=60
```

**为什么用 RRF 而不是加权求和**：向量分是余弦相似度（0~1），BM25 分是无界实数，两者**量纲不同**，直接加权需要调一个没有理论依据的系数。RRF 只看名次不看分数，天然规避了这个问题。

**然后是重排（rerank）**：
- 一阶段双塔：快但粗，召回 **top-20**（广撒网）
- 二阶段交叉编码：把"查询+文档"拼起来过一遍模型，慢但准，取 **top-3**（精准命中）

**代价是可量化的**：重排每条 query 多一次 API 调用、多几百毫秒。**这笔账值不值，消融实验里用数字回答**——不是拍脑袋说"重排很重要"。

## 4. 评测层：金标是怎么来的

**方法一：合成评测集（主）**

流程：抽一份准则 → 让 LLM 基于它生成 2 个业务问题 → **这份文件就是天然的金标**。

关键约束：生成问题时**禁止照抄标题、文号、独有原句**。
否则问题里直接含"金融工具列报"，纯关键词检索就能命中，测不出语义能力。

**代价**：这类问题偏"可直接查到"，真实用户会问更含糊、需要跨文件综合的问题。
所以要加第二个子集（见下）。

**方法二：实案子集（辅）**

毕设里有 292 个真实企业算例和已有的政策匹配结论，可以构造"给定企业画像→应适用哪些政策"的问题，金标来自真实匹配结果。
这批问题更贴近实际使用。

**为什么不用 RAGAS 全自动**：LLM 裁判本身有噪声，自动指标不能当 ground truth。
本项目的用法是：自动跑 + 抽样人工复核，报告里明确标注这个局限。

## 5. 指标口径：一个必须讲清的细节

**doc 级还是 chunk 级？** 本项目用 **doc 级**——用户要的是"找到对的那份政策"，不是"找到对的第 37 个字"。

**先截断还是先去重？** 这是实现时被单元测试抓出来的一个真 bug：

```
检索结果 ["政策A", "政策A", "政策B"]，金标是 政策B，k=2
```

- 先去重再截断 → `["A","B"]` 取前 2 → 命中 → Recall=1.0 ❌ **虚高**
- 先截断再去重 → `["A","A"]` 折叠 → `["A"]` → 未命中 → Recall=0.0 ✅

同一份政策占两个名额，意味着它**挤掉了另一个可能相关的政策**，这个代价必须体现。
先截断再去重才是诚实的口径。测试文件 `tests/test_metrics.py` 里锁住了这个行为。

## 6. 成本口径：不报成本是常见减分项

只看 Recall 不看价，等于没说。任何一条结论都要能回答"值不值"。

所以每次实验同时记录：

- **延迟**：p50 / p95（重排是延迟大头）
- **API 调用次数**：embed 几次、rerank 几次、rerank 了多少个文档
- **效果**：Recall@1/@3、MRR、nDCG@3、P@3

四条曲线放在一张表里，才能说"加这 600 毫秒换来多少 Recall"。

## 7. 已知的局限（主动写出来，比被问出来好）

1. **合成评测集偏"能直接查到"**——真实场景的问题更模糊，指标会乐观。
2. **LLM 裁判有噪声**——faithfulness 分数只作参考，需人工抽样校准。
3. **没有做多跳问题**——"这家企业同时满足 A 和 B 准则时该怎么处理"这类需要跨文件推理的问题未覆盖。
4. **语料是抓取快照**——财政部网站的页面会更新，本项目锁定在某次抓取，不追增量。
5. **只用了一种 embedding**——bge-m3。跨 embedding 的对比（如 m3e、C-MTEB 其他模型）留作后续。
6. **切分结论有适用边界**——"切分不重要"是 doc 级金标下的结论，换成片段级金标或 top-1 下游会变。
7. **发布日期有噪声**——31/549 份共用 `2008-05-22`（疑似站点改版时间），91/384 份的发布日期年份与文号年份不一致。做"按年份硬过滤"之前要先清这批。
8. **拒答门未真正生效**——链路里做了阈值拒答，但 30 条生成评测样本上拒答率 0%，一次都没触发。阈值需要按分布重标定。
9. **`valid_to` 在本语料上为空**——会计准则不用"执行至…"的措辞。该字段是为换语料（如税收优惠）预留的，本语料的时效过滤靠 `issued`。

## 8. 与业界做法的对照

| 业界做法 | 本项目 | 差异原因 |
|---|---|---|
| RAGAS 全自动评测 | 自动 + 抽样复核 | LLM 裁判有噪声，不做唯一依据 |
| BEIR / MTEB 基准 | 自建领域评测集 | 通用基准测不出财会准则这个垂直域的表现 |
| GraphRAG / 知识图谱 | 不做 | 构建成本极高，多数场景不如"混合检索+重排"，性价比存疑 |
| Agentic RAG | 在配套的 Agent 项目中做 | 检索质量是前提，先把它做扎实 |
